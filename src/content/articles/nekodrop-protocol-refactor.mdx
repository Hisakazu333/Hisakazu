NekoDrop 的传输协议终于要重构了。这个决定拖了三个月——每次想动手，都觉得"现在还能跑"。直到上周加一个小功能改了十七个文件，我知道不能再拖了。

## 问题出在哪

最初的协议设计是"能跑就行"：一个硕大的消息体，所有字段平铺，靠一堆 `if-else` 分发处理。当时只有三种消息类型，这样写确实快。现在消息类型有十四种，悲剧就发生了：

```typescript
// 重构前：一个函数认识所有消息，所有消息害怕一个函数
function handleMessage(msg: FlatMessage) {
  if (msg.type === 'chunk') { /* 80 行 */ }
  else if (msg.type === 'ack') { /* 60 行 */ }
  // ……还有十二个 else
}
```

## 重构的三条原则

这次重构我给自己定了三条规矩：

1. **消息即类型**。每种消息一个类，自己负责序列化与校验，协议层只做路由。
2. **版本先行**。协议头里第一个字段永远是版本号，哪怕现在只有 v1。
3. **先写坏消息**。把"失败时发生什么"写在文档里，再开始写"成功时怎么做"。

## 结果

重构用了四个晚上。代码行数减少了 40%，但更重要的是——加第十五种消息类型的时候，我只改了一个文件。

> 重构不是为了让代码变漂亮，而是为了让下一次修改不再可怕。

教训也有一条：丑话（约束、边界、失败路径）要趁早说。说晚了，就得用四个晚上来补。
